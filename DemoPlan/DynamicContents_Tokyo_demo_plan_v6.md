# DynamicContents — Tokyo demo plan (v6)

*Cold-reader document, written 2026-09-21 by Claude (chat session, DynamicContents Project) at Kavin's request. Companion to `README.md` (system overview + Claude's read) and the six figures in `diagrams/`. **Supersedes v5, v4 and v3.***

**Status: the plan is DONE. Every build item in it is FUTURE — nothing is in flight.**
Build tooling (Kavin's call): Codex Astra plus Claude. Build time is not the constraint; a proper demo is.

### What changed from v5 (Kavin's ruling, 2026-09-21)
- **Everything is name-agnostic.** No game titles, no building, brand or shop names — real or fictional — anywhere in the demo or in this document. Games are Game A and Game B, slots are A1–A3 and B1–B2, content is Content 1–4, rivals are "the rival" for a region. A brand's identity is a colour plus a simple emblem.
- **"Push an update" is confirmed** as part of the tour (step 9).
- Nothing else changed.

### What changed from v4 (Kavin's direction, 2026-09-21)
- **The bidding portal is the star of the demo.** Upload content → pick a game → see its slots on a map with footfall → pick regions → bid in a timed auction with fake money → win → the content goes live in the running game by itself.
- **Two games** in the portal, both real: one packaged build with two maps (Game A, the larger one, and Game B, a small one).
- **Regions.** Each region is auctioned separately. A second copy of the game, set to another region, shows that a win in Japan does not appear in India.
- **The slot map is generated by the UE plugin** from the real level.
- **The Player side is a plain tech demo:** walk around, go inside the content, use doors, lights and screens. No stamp rally, no tokens, no wearables, no money.
- Dropped: player profiles, day/night, lite packs, the low-spec "Player B" idea (replaced by the region preview window).

## 1. The demo in one paragraph

One PC, two monitors, two controllers. **One controller per role.** Controller 2 is the **Brand** (right screen): they pick a colour and emblem for their brand, upload a piece of content, choose one of two games, look at that game's slot map with footfall per slot, choose regions, and bid fake credits in a short timed auction against a rival brand. When the auction closes and they win, they do nothing else — the content appears in the running game on the left screen as soon as the **Player** (controller 1) walks near that spot, and stays for a fixed number of hours. A small preview window shows the same game for a player in another region, where a different, local winner's content appears instead. The game build starts in the morning and never restarts.

**Plain-words glossary**

| Word | Meaning here |
|---|---|
| Slot | A fixed spot in a game map where content can be swapped in at runtime |
| Content | A walk-in structure a brand uploads. Generic and unthemed; told apart by shape, colour and emblem |
| Pack | The file for one piece of content (a pak / container set) |
| Slot map | A top-down picture of a game map with a pin on every slot, made by the plugin |
| Footfall | Views a slot gets per demo hour, per region ("footprints") |
| Region | Where a player is playing from. Japan, India, Europe in the demo |
| Lot | The thing being auctioned: **one slot × one region × one time block** |
| Time block | 3 demo hours |
| Demo clock | 1 demo hour = 1 real minute. Always labelled "demo time" |
| Held credits | Credits set aside while you are the highest bidder. Released if outbid, charged if you win |
| Rival | An unnamed competing brand, scripted by the server, that bids against the visitor. One per region, shown only as a colour and emblem |
| Default content | What the game's developer shows in a slot when nobody has bid |
| Status strip | Small always-on strip on the left screen showing what a slot is doing right now |
| X-ray view | Optional overlay: pre-fetch ring on the ground, the manifest, the cache list |

| | Player seat (left) | Brand seat (right) |

Everything runs on the one PC: the game, a second copy of the game (the region preview), the portal (a web page), the local server + storage (the stand-in cloud), the pad helper, and a start script with a watchdog.

## 3. The two games and the Player side

One packaged build, two maps. The Player picks a game from a title menu and can switch from the pause menu.

| Game | Size | Slots |
|---|---|---|
| **Game A** | Main map | A1 (large, highest footfall), A2 (large, tall content allowed), A3 (small) |
| **Game B** | Small map | B1 (large), B2 (small) |

- The two maps are neutral, unthemed environments that look clearly different from each other (layout, palette, lighting) so they read as two different games. Neither has a title.
- The Player simply walks around in third person and goes inside the content. Each piece of content has a few plain interactable things: a door, light switches, a display screen that cycles images. That is all — it is a tech demo, not a game.
- When a slot's content changes, a neutral waypoint marker points to it. No ad or money language ever appears on the Player's screen.
- Switching between the two games is a normal level load, because it is switching games. The promise being shown is that **content** changes never need one. The strip on the left screen shows, all day: **build number · uptime · restarts: 0 · content loading screens: 0.**
- The main screen plays as a player **in Japan**.
- A slot with no winner shows the developer's default content (a plain, unbranded placeholder).

## 4. The flow — full tour, about 5½ minutes

Brand seat unless stated. The Player walks around freely the whole time.

| # | Step | What happens | Patent promise shown |
|---|---|---|---|
| 0 | **Attract** (idle) | Auctions tick over among the rivals; content changes as time blocks roll over; slow camera over the map | Time-window allocation, live refresh |
| 1 | **Create your brand** 0:00 | Pick a colour and an emblem (a simple shape) from presets. They appear on your content's sign later. No names. Wallet: 2,000 demo credits | Brand account |
| 2 | **Upload** 0:15 | Choose a pack file from "your computer" → real upload with a progress bar → real checks: package, engine version, size, rating, sign → "Approved" in My content. One file is built to fail, with a reason | Content upload; the validate → moderate → sign gate; reject with diagnostics |
| 3 | **Pick a game** 0:45 | Two games listed, each with slot count and players online. The one being played at the booth is badged | Multiple compatible games on one platform |
| 4 | **Slot map** 1:00 | Plugin-generated top-down map, pins coloured by footfall. Slot card: eye-level thumbnail, size and rating rules, footfall per region, current highest bid and who holds it, closes in mm:ss, price per 1,000 views. Slots the content does not fit are greyed out with the reason | Slot contract (bounds, rules); footfall from telemetry |
| 5 | **Regions and bid** 1:15 | Tick regions (default: Japan). Table per region: footfall · highest bid · your bid · status. Bid → credits held. The rival counter-bids once → "outbid in Japan" → raise → clock runs out → **won**. Held credits charged; lost regions released | Campaign setup and bid; auction; allocation per slot per region per time block |
| 6 | **It goes live by itself** 2:15 | No publish button. Player sees the waypoint; walking near the slot triggers resolve → download → verify → mount on the status strip; the content appears with the brand's colour and emblem on the sign; Player walks in | Full runtime sequence; no loading screen; no action needed by the brand |
| 7 | **Region check** 3:00 | The region preview window appears: same game, same slot, a player in India → the India rival's content is there, not yours. Flip it to Japan → yours. If the visitor also won India → theirs in both | Context-driven variation; region filtering |
| 8 | **Report** 3:30 | Views, visits, dwell, interactions, credits charged, cost per view, by region; time left. Pause button | Telemetry; reporting dashboard |
| 9 | **Push an update** 3:50 | Upload version 2 of the live content. If the Player is inside, nothing changes until they walk out; then it swaps; when they walk back in, the lights, door and screen are as they left them | Post-deployment replacement; deferred swap; state preservation |
| 10 | **Block ends** ~5:15 | The 3 demo hours run out; the next block's winner swaps in. Summary card: credits spent, views, visits, dwell, cost per view, by region | Time-window allocation; the full loop |

Then automatic reset back to step 0.

### Notes on the steps

**Step 2 — Upload.** The files are pre-cooked and sit in a folder that plays the part of the brand's computer; the visitor cannot bring their own. But the upload itself is a real HTTP upload and the checks really run on the uploaded file.

**Step 5 — The auction.** The clock starts at 0:45 when the visitor places their first bid. A bid in the last 10 seconds resets the clock to 0:10 (soft close, so nobody loses to a last-second snipe). The rival is scripted to bid once more and then stop below what the wallet can beat, so a visitor who tries can always win. A visitor who lowballs or walks away loses, and the rival's content is what appears — also a valid demo. Staff can force the close with a button combo.

**Step 6 — By itself.** Winning writes the allocation; the game finds out by polling; the content is fetched when the Player nears the slot, exactly as in the runtime sequence figure. If the Player is already standing inside the old content, the swap waits until they leave.

**Step 7 — Region check.** In production the region comes from the player's account or locale. Here it is a setting on the second copy of the game, switchable from the portal. The window is only shown during this step so the portal has the full screen the rest of the time.

**Step 9 — Push an update, in plain words.** A brand will want to change its content while it is live: new sign, new layout, a fix. The patent's promise is that this never interrupts a player. If someone is inside when the new version arrives, the game keeps the old one until they walk out, then swaps, and carries over whatever they had changed inside (here: which lights are on, whether the door is open, which image the screen shows). Version 2 of each piece of content looks visibly different so the swap is obvious.

### Express version (90 seconds, for crowds)
Brand preset and content already approved → one slot, Japan only → staff closes the auction early → it appears.

### Staff tricks (for "what if it fails?")
- **Corrupt pack:** a button combo makes the server send one corrupted pack → hash mismatch → default content stays → retry with backoff → success.
- **Frozen download:** a second combo pauses the server mid-download for a few seconds → the download resumes from where it stopped rather than starting over.

## 5. How regions and bidding fit together

**The rule: every region runs its own auction for the same slot.** What is sold is a *lot* — one slot, one region, one time block. A multi-region campaign is just several bids placed at once. Bids are never compared across regions.

Worked example, slot A1:
- A local brand bids 300 for Japan only.
- A global brand puts 600 across five regions. The portal splits it by footfall (adjustable): Japan 180, India 150, North America 140, Europe 90, SE Asia 40.
- In Japan, 300 beats 180 → the local brand wins Japan. The global brand wins the other four.
- The portal tells the global brand: "winning 4 of 5 · outbid in Japan by 120 · top up?"

So a big multi-region budget cannot steamroll a local bidder; it only wins a region if its share for *that* region is the highest there. Each region's opening price scales with that region's footfall, and the portal shows **credits per 1,000 views** so a large and a small region can be compared on value.

The demo uses three regions to keep the table small: **Japan** (the main screen), **India** (the preview window's default), **Europe**.

## 6. The slot map: how the plugin makes it

An editor-side tool in the plugin (it never runs in the shipped game):
1. Takes a straight-down orthographic capture of the level and saves it as an image.
2. Finds every slot actor and records: slot ID, position, size limits, rating rule, allowed categories, pre-fetch radius.
3. Converts each slot's world position into a pixel position on the image.
4. Takes a eye-level thumbnail from a viewpoint attached to each slot.
5. Uploads the image, the thumbnails and a small JSON file to the platform (`register game`).

The portal draws the image with a pin per slot. Pin colour comes from footfall, which comes from runtime telemetry. For the demo this tool is run for real on both maps before the expo; an optional 15-second clip shows the button being pressed in the editor.

This is also the missing third actor in the story: **the game developer**, who registers the game, its slots and the rules for each slot.

## 9. How the pieces work (starting values — tune in testing)

### The local server (the stand-in cloud)
One small program plus S3-compatible storage (MinIO) on the same PC. The game talks to it exactly as it would talk to the real backend.

| Call | Purpose |
|---|---|
| `POST /games/register` | From the plugin tool: map image, thumbnails, slot list and rules |
| `GET /games`, `GET /games/{id}/slots` | Portal: games list; slot map, pins, rules, footfall by region, open lots |
| `POST /content`, `GET /content` | Upload a pack → checks → approved / rejected with reasons; My content |
| `POST /content/{id}/versions` | Push an update (version 2) |
| `POST /bids`, `GET /lots/{id}` | Place or raise a bid per region; live auction state and countdown |
| `GET /resolve` | Game: slot + game + region in → signed manifest out (pack ID, version, hash, URL, class path, brand colour and emblem) |
| `GET /changes` | Game polls every 1–2 s to learn that a slot's allocation changed |
| `POST /telemetry`, `GET /report` | Views, visits, dwell, interactions in; per-campaign, per-region report out |
| `POST /campaign/pause` | Brand's pause button |
| `POST /admin/reset`, `/admin/sabotage`, `/admin/close-auction` | Booth housekeeping and the staff tricks |

Pack downloads are paced in local mode so they take 3–5 seconds. Still a real HTTP download and a real hash check.

### Footfall seeds (views per demo hour)

| Slot | Japan | India | Europe |
|---|---|---|---|
| Game A · A1 | 1,200 | 900 | 600 |
| Game A · A2 | 800 | 600 | 400 |
| Game A · A3 | 300 | 250 | 150 |
| Game B · B1 | 700 | 500 | 350 |
| Game B · B2 | 250 | 200 | 120 |

### Auction rules
- **Opening price** of a lot = footfall × 0.25 (A1 / Japan opens at 300). This is shown as the rival's current highest bid.
- **Rival:** one unnamed local brand per region. After the visitor's first bid it raises once to beat them, never above 2 × the opening price. The wallet can always beat that — even all three regions of slot A1 cost at most 1,350.
- **Minimum raise:** 25 credits. Pad shoulder buttons step the bid.
- **Clock:** 0:45 from the visitor's first bid; a bid in the last 10 s resets it to 0:10.
- **Multi-region:** tick regions, enter one total, the portal splits it by footfall; adjust per region.
- **Credits:** held while leading, released when outbid, charged on a win. Wallet shows available and held.
- **Winner:** highest bid per lot. A lot with no bids shows the developer's default content.
- **After a win:** the allocation is written for the time block starting now; the content lasts 3 demo hours (3 real minutes). Meanwhile the next block's auction runs among the rivals; the visitor can rebook from the report.

### Content checks, in order
Package (exists, size, engine version tag) → content rating → sign (hash + signature with a demo key). Fit against a slot's size limits is checked when choosing a slot. Only content that passes becomes biddable; the game never mounts an unsigned pack.

### State kept across an update
A small record keyed by slot + content + schema version: lights on/off, door open/closed, screen image index. Saved on unload, restored on spawn. Versions 1 and 2 share the schema. If schemas ever differ: migrate or discard, never crash.

### Telemetry definitions
- View: content on screen, within 30 m, at least 1 s, not blocked (simple line check).
- Visit: the Player enters the slot's bounds. Dwell: seconds inside.
- Interaction: each use of a door, switch or screen.

### Reset
Triggered by 60 s idle or a 3-second staff combo on pad 2. Wipes: the visitor's brand, wallet, uploads, bids and allocations, counters, saved state, and the visitor's packs from the local cache (so every visitor sees a real download; rival and default content stay cached).

## 11. Technical calls already made

- **The game keeps window focus all day.** The portal is driven through the pad helper, not by clicking, so nobody clicks outside the game.
- **Insurance anyway:** borderless windowed (never exclusive fullscreen), no frame-rate throttle and no audio mute when unfocused — so an emergency mouse click on the right screen is survivable.
- **Controllers wired by USB, never Bluetooth.** At startup: "press ✕ on the player pad" → the game locks to that pad, the helper takes the other.
- **Pad helper** reads pad 2 with background input enabled and relays to the portal over localhost. This path never goes through the cloud.
- **Region preview budget:** 30 fps cap, half resolution, lowest settings, below-normal process priority, its own pack cache folder. Main game at high priority.
- **Region preview pass/fail:** the main game must hold its frame rate with the preview alive through a soak run. If not, drop the preview and do step 7 as a live flip: the portal switches the main game's region to India and the slot swaps in front of the Player.
- **One-button start:** storage → server → portal on the right monitor → game on the left → region preview, in order, with health checks; a watchdog restarts anything that dies.
- **Portable:** the whole demo is one self-contained folder (relative paths, no installers), copied to a USB drive next to the backup video.

**Day-1 checks (before anything else is built on top):**
1. The game listens to pad 1 only.
2. The helper reads pad 2 while the game has focus.
3. Two copies of the game run side by side.
4. The game keeps running, rendering and playing audio when unfocused.

## 13. Local mode vs AWS mode

One server codebase, two homes.

| | Local mode (floor default) | AWS mode (a switch) |
|---|---|---|
| Server | Normal program on the PC | Same code in Lambda behind API Gateway (Lambda Web Adapter, no rewrite) |
| Files | MinIO | S3 (same API; config change), presigned URLs, CloudFront optional |
| Data | Small database file | DynamoDB |
| Transport | HTTP on localhost | HTTPS |
| Download pacing | On (3–5 s) | Off — the real network provides it |

- The game and portal read one setting: the backend address. Switch only at reset, never mid-visitor.
- The start script health-checks the cloud and falls back to local if there's no answer.
- Use AWS mode for the viability demo at the office and for "now it's coming from the Tokyo region" moments when the venue link is good. Internet is **not** on the guaranteed list, so the booth must never depend on it.
- Tokyo region for the expo, Mumbai for office testing. Write endpoints protected with a key; bucket private.

## 14. Order of work, each with an exit test

1. **Allocation → appear.** Server, storage, polling, resolve with region, status strip, day-1 checks. *Exit: a hand-written allocation makes the content appear, ten times out of ten.*
2. **Slot-map tool, games list, slot map page.** *Exit: on both maps every pin sits where the slot really is.*
3. **Brand creation, upload, checks, My content, colour and emblem on the sign.** *Exit: a good file is approved, the bad file is rejected with a reason, the sign shows the chosen colour and emblem.*
4. **Auctions.** Lots, rivals, clock, held / charged credits, region table, allocation. *Exit: a pair of strangers goes from "create your brand" to walking into their content unaided. This is the minimum viability demo — record a clean capture that day; it is the submission video and the permanent fallback.*
5. **Region preview window** and its pass/fail test.
6. **Report, push an update with state kept, block expiry, attract mode.** *Exit: step 9 works ten times out of ten, including when the block ends while the Player is inside.*
7. **Hardening, then feature freeze.** Three overnight soak runs: a scripted bot cycles bid / win / mount / update / expire 500+ times while logging memory and frame time — pass = flat memory, no stutter. Failure drills: kill the server mid-download, serve a corrupt pack, unplug a pad. The visitor must only ever see default content, never an error. Staff cue cards (JP/EN), pack list.

Step 7 is not optional however fast the code gets written. Fast-written code is exactly what a soak test is for.
